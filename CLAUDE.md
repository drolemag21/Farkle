# Farkle Table

Classic Farkle for 2-4 players online, in one HTML file (`farkle-table.html`). It runs in two places from that one source:
- **Claude Artifact**: published with the Artifact tool, players connect through the Artifact's built-in room.
- **GitHub Pages**: `docs/index.html`, generated by `node tools/build-site.js`, players connect through Supabase Realtime. Anyone with the link can play.

## Read first
- `HANDOFF.md`: where the project stands, links, the Supabase setup, and how to ship a change.
- `NOTES.md`: how the code is organized (networking, physics, sound, rendering, function names). Keep it current when you change a system.

## Working with the owner
- Bring up design and structural suggestions on your own when they'd pay off. Keep them brief, explain the payoff, and propose rather than silently doing big refactors.
- Discuss design before building when the owner is exploring ideas; build when they say go. They often ask for a plan or options first.
- Explain trade-offs with a recommendation, not an exhaustive survey.
- The owner tests on phones: keep everything usable at 375 px wide.

## Publishing
- **Artifact:** publish `farkle-table.html` with the Artifact tool and capabilities `{"room": {}}`. Republishing the same file path in the same conversation keeps the link. From a new conversation, read the link recorded in `NOTES.md` and pass it as `url`, or a separate artifact is created. A different Claude account can't update another account's artifact: its first publish makes a new link (record it in `NOTES.md`).
- **GitHub Pages:** `docs/index.html` is generated from `farkle-table.html`. Run `node tools/build-site.js` after every change and commit `docs/` with the source. Never edit `docs/index.html` by hand. GitHub Pages redeploys on push (serving `/docs` from `main`).
- A change usually ships twice: republish the Artifact, and rebuild + push `docs/`.
- `site.config.json` holds the Supabase project URL and the **publishable** key (`sb_publishable_...`). Both are public by design. Never put a secret key (`sb_secret_...`) or a legacy service_role key in this repo; the build refuses anything that isn't a publishable key.

## Testing
- `.claude/launch.json` has two servers for the browser pane:
  - `farkle-table` (:8765): the source. Open `/farkle-table.html` in two tabs and pick Settings → Network → "This device only".
  - `farkle-site` (:8766): the built `docs/`. Open `/index.html`; it connects to the real Supabase project, so two tabs make a real online game.
- Close old game tabs and test in fresh ones; leftover timers corrupt results.
- On localhost the page exposes `window.__farkle` (state `S`, `toggleDie`, `pickDie`, `canAct`, `scoreOf`, `SND`, `poses`, `setDiceColor`, ...) for scripted tests.
- A hidden browser pane delivers no real clicks and may not draw frames: drive tests with `.click()` from JavaScript and don't wait on animation-frame-only state.
- Synthesized sound can't be heard here. Check that it plays without errors and compare levels with `__farkle.SND.measure(part)`.
- Verify a change in the browser before publishing, and say plainly what was and wasn't covered.

## Code conventions
- Everything lives in one HTML file: CSS tokens on `:root`, markup, then one script IIFE. Deliberately single-theme (a casino table at night).
- The host is the only writer of game state; clients render snapshots and play effects for events. Anything that comes from another browser goes through `cleanState`, so new state fields must be added there too.
- The dice physics must stay deterministic across browsers: only + - * / and sqrt in `simulate`.
- Match the surrounding comment density and naming; comments explain why, not what.
